## One architecture: a headless satellite and the aggregator

RDS Guard is now always two containers ([plan](../plans/satellit-aggregator.md)):

- **The satellite** (`ghcr.io/tubalainen/rds-guard`) only receives and records. It has no web UI, no MQTT, no transcription and no map, and it **needs an aggregator**: without `AGGREGATOR_URL` it stops with a message saying so.
- **The aggregator** (`ghcr.io/tubalainen/rds-guard-aggregator`) does everything else, for any number of satellites: the archive and web UI, transcription, the map, Trafikverket, push and MQTT.

The default `docker-compose.yml` runs both on one host. The web UI is the aggregator's, on port **8080**. Port 8022 is gone.

### The satellite

- **Several dongles, by serial number.** `rds-data/receivers.yml` lists the dongles, each with up to four stations within 2 MHz (see `receivers.example.yml`). A dongle is always known by its serial number, never by its USB order. `docker compose exec rds-guard python3 -m dongles` lists them; two with the same serial number are refused, with the `rtl_eeprom` command that fixes it. With one dongle, `FM_FREQUENCY`/`FM_FREQUENCIES` in `.env` are still enough.
- **Gain and ppm are found automatically,** for each dongle and all its stations together.
  - **How:**
    1. It measures the frequency error from the stations' carriers.
    2. It sweeps the gain steps for clipping and pilot/RDS signal-to-noise.
    3. It checks the four best steps with real RDS decoding.
    4. It picks the step where the worst station decodes best.
  - **When it runs:**
    - at the first start (about two minutes per dongle; only that dongle pauses)
    - when a station decodes much worse for 15 minutes
    - from **Admin → Noder → Kalibrera om**

    It never runs during a broadcast.
  - **Fixed values:** `gain:`/`ppm:` in `receivers.yml`. `RTL_GAIN` and `PPM_CORRECTION` in `.env` are no longer used (a line in the log says so).
- **Every station goes through the same chain:** `rtl_sdr` → channelizer → `redsea`, one station or four. `rtl_fm` is gone.
- **Health without a port.** `docker compose ps` shows the satellite as `healthy` while a dongle receives. `docker compose exec rds-guard python3 -m satellite_health` says why if not.
- **Its own small database, `satellite.db`,** and recordings in `rds-data/spool/`, kept for 7 days after delivery (`SATELLITE_KEEP_DAYS`).
  - At the first start it moves its identity (token, approval) and anything not yet delivered from the old `events.db`.
  - `events.db` and `audio/` are left untouched, for the import.
- **The image is much smaller:** no Whisper model, no web UI, no MQTT client. It suits a Raspberry Pi.
- **The first TA flag after a start** no longer ends a broadcast that never began.

### The aggregator

- **A satellite asks to join.** It needs only the aggregator's address (`AGGREGATOR_URL`).
  - **The request:** without a token it makes its own and asks. It shows up under **Admin → Noder → Väntar på godkännande** with its stations, suggested place and a code like `K7Q-3PD`. The satellite's log shows the same code.
  - **The choices:** **Godkänn**, **Avvisa**, or **Ersätt befintlig nod**, which keeps that node's history.
  - **Command line:** `python3 -m aggregator.nodes pending | approve <code> | reject <code>`.
  - **`JOIN_KEY`:** the same secret on both sides approves the satellite at once. In the shared `.env` of `docker-compose.yml`, that is all a new installation needs.
  - **Until it is approved,** the satellite records and queues everything.
- **One broadcast is one event, even when several satellites or dongles hear it.**
  - It is transcribed once (the longest recording), and alerted and pushed once.
  - **Hörd av** on the event shows each node and dongle that heard it, with its own recording.
  - A node that goes silent mid-broadcast does not hold the alert.
  - Removing a node keeps what the others heard.
  - Push rules limited to a node match every broadcast that node heard.
  - The MQTT alert gains `nodes`.
- **The node card shows each dongle:** its state, gain and ppm (automatic or fixed), when it was calibrated, and its stations with decode rate. The card also has **Kalibrera om** and **Ändra plats**.
- **A new broadcast is reported at once,** even while a recording uploads: events and audio travel in two queues, and a recording always goes after its event. Unsent items are kept for 7 days (`UPLINK_MAX_AGE_HOURS=168`).
- **`python3 -m aggregator.retranscribe`** transcribes the archive again, with `--node` to pick one node.

### What is gone

- The satellite's web UI and API (port 8022) and the **Debug** page with its live RDS console.
- The satellite's MQTT: the topics per RDS group (`programme/rt`, `station/pty`, `traffic/tp`, `system/status`, `PUBLISH_MODE=all`) and EON (group 14A). The aggregator's `alert`, `notify/…`, `{pi}/traffic/ta` and `{pi}/{type}/transcription` are kept.
- `LOCAL_PROCESSING` and standalone mode.
- WAV recordings (`AUDIO_FORMAT`).
- `RTL_DEVICE_INDEX`: use the serial number.

## Upgrading

Satellites and the aggregator speak protocol 2 and must be updated **together**:

- An aggregator answers a v0.10 satellite with "update needed".
- A v1.0 satellite gets the same answer from a v0.10 aggregator.

Nothing is lost while they wait. But a v0.10 satellite drops queued items after 72 hours, so update both within that time.

First back up both data folders:

```bash
docker compose down
```

```bash
sudo cp -a rds-data rds-data.backup-0.10 && sudo cp -a aggregator-data aggregator-data.backup-0.10
```

### Satellite and aggregator on one host (as on docker01)

1. Get the new compose file. Keep `.env`, `rds-data` and `aggregator-data`:

```bash
curl -fsSLo docker-compose.yml https://raw.githubusercontent.com/tubalainen/rds-guard/master/docker-compose.yml
```

2. In `.env`:
   - The `UPLINK_TOKEN` or `JOIN_KEY` you have keeps working; leave it.
   - Remove `RTL_GAIN` and `PPM_CORRECTION`, so the satellite finds them itself. To keep a fixed gain instead, put it in `rds-data/receivers.yml` (see `receivers.example.yml`).
   - The satellite settings it no longer uses (`WEB_UI_PORT`, `PUBLISH_MODE`, `LOCAL_PROCESSING`, `SATELLITE_MQTT_ENABLED`, `AUDIO_FORMAT`, `RTL_DEVICE_INDEX`) can go. They are only warned about.
3. Start:

```bash
docker compose pull && docker compose up -d
```

4. Check:
   - `docker compose logs -f rds-guard` shows the move from `events.db`, `calibrating gain and ppm`, one line per gain step, then `calibrated: gain … ppm …`, and RDS from the stations.
   - After about two minutes, `docker compose ps` shows the satellite `healthy`.
   - **Admin → Noder** shows the dongle with its gain, ppm and decode rate.
5. Point bookmarks and the reverse proxy (`rds.tuben.org`) at port **8080** instead of 8022.

If you never added the aggregator (one `rds-guard` container up to v0.10): do the same, then import the history before you look for it. The README's *Importing an installation's history* has the two commands. Put the `UPLINK_TOKEN=…` line the import prints in `.env`, and run `docker compose up -d`.

### A satellite on its own (friends' satellites)

```bash
curl -fsSLo docker-compose.yml https://raw.githubusercontent.com/tubalainen/rds-guard/master/docker-compose.satellite.yml
```

```bash
docker compose pull && docker compose up -d
```

- `.env` needs `AGGREGATOR_URL` (`UPLINK_URL` still works). An existing `UPLINK_TOKEN` keeps working.
- Remove `RTL_GAIN` and `PPM_CORRECTION` as above.
- The local web UI and MQTT are gone. The aggregator's owner sees the satellite under **Admin → Noder**.

### Rolling back

Pin **both** images to `0.10.3` in `docker-compose.yml`:

- `ghcr.io/tubalainen/rds-guard:0.10.3`
- `ghcr.io/tubalainen/rds-guard-aggregator:0.10.3`

Use the old compose file from the v0.10.3 tag, which still publishes port 8022, and restore the two backups. v0.10.3 does not read `satellite.db`. Restoring the backups loses what was recorded while v1.0 ran.
